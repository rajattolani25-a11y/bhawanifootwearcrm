# Catalog sale promotions

The owner approved the bold streetwear direction, then asked for a smaller, less insistent presentation. The final built-in presets are compact inline cards: restrained angled headline labels, muted print texture, one/two product thumbnails at the side, and a clear action row. Oversized arrows, starbursts and neon buttons are removed. Spotlight remains first. No popup, page-opening intro, autoplay sound or floating promotion is added.

## Owner workflow

Left menu → Catalog Studio → Offers & coupons → Sale promotions. Everyone / Men / Women have independent enable state, title, message, existing coupon, selected existing products (0–2), advance/live artwork and schedule. Both phases offer Street Drop and Sticker Edit. Product selection order is preserved in preview and storefront. Customer Men/Women filters show the corresponding campaign; Everyone campaigns are shared. These are promotion audiences, not new server-side coupon department restrictions.

One product gets a larger thumbnail; two products form a compact pair of thumbnails. Covers are reused without uploading duplicates. The photos remain the actual selected products. Product clicks open the exact product. Custom owner posters replace the preset artwork and retain their full original aspect ratio; no overlay lettering/cropping is applied. The original title and full conditions remain available in user-opened offer details.

The initial preview is Live sale, matching an unscheduled campaign. With scheduling OFF, only Live artwork is shown publicly; Advance artwork requires announce/start/end times. Selecting a custom photo opens that phase's preview. A saved visibility panel checks the actual public promotion RPC, showing master/audience OFF, upcoming/ended phase, unavailable coupon/catalog or the current visible phase. Unsaved previews are explicitly distinguished from saved publication. Save refreshes this status and warns if an enabled campaign remains hidden. Expired/exhausted coupons remain labelled and disabled in the selector rather than looking usable. Current financial checkout rules are unchanged. Saving also signals an already-open catalog tab on the same origin; visibility/poll refreshes remain as fallback. Signing transport failures retain configuration and use existing image/preset recovery instead of dropping the whole promotion.

Read-only live inspection on6November2026 confirmed that the Everyone campaign was enabled, with notice03:05AM, live03:06AM and end03:07AM IST on6November. The valid public DTO computed `hidden` after that end time; save was working. The owner then requested SQL. `show-expired-everyone-live.sql` is a separate optional manual settings fix: it removes only that expired enabled Everyone schedule, preserving the saved Live artwork and other audience/config/coupon fields. It refuses OFF gates and non-expired schedules; unavailable public coupon/catalog rolls the change back. Reapplying to an already unscheduled public campaign is harmless. It does not execute a sale, reset, deletion, upload or financial-function replacement. Reload open owner forms after application to avoid saving a stale draft. It is not part of automatic migrations or the upload installer, and was not applied live by the agent.

## Storage and production setup

The owner subsequently approved existing shop photo storage for custom uploads, superseding the original external-only preference. No Cloudinary account or API secrets are needed. The existing **private** `catalog-hero-images` bucket is reused under `promotions/<audience>/<phase>/<UUID>.webp`; product photos and `hero/...` paths are not replaced or deleted by promo cleanup.

JPG/PNG/WebP input up to10MiB is compressed in-browser to WebP, up to1600px and400KiB. Unreadable, unsupported or still-too-large images produce a clear error. Existing small WebP files are retained within the limit. Only paths, dimensions and byte counts are stored in bounded `store_settings.offer_promotion` JSON (maximum16KiB), never binary/base64 or expiring signed URLs. There are six configured image slots (3 audiences ×2 phases), at most2,457,600bytes of active native poster files at the per-file limit. During replacement/staging, old and new files can temporarily coexist.

Run the complete **`docs/sql/catalog-promotions/photo-storage.sql`** once, then **`verify-photo-storage.sql`** (four true values). This is a complete installer under200lines, works with or without the earlier base promotion SQL, and can be reapplied. Do not replay the older base installer after it; the repository base script now refuses to downgrade installed native-photo support. No SQL was applied live during this work. The installer changes presentation/photo policies, queue reason allowlist and promotion settings functions only; it does not execute reset/file deletion or replace billing/stock/reset/restore definitions. It uses existing buckets/tables and notifies PostgREST to reload schema. Publish the matching frontend after installation.

Preparation verifies the signed-in owner. Uploads use the existing Storage API with `upsert:false`. Save validates the audience/phase path, WebP MIME and actual uploaded file size, then commits settings and queues replaced paths in the same transaction. Saved promo paths are delete-protected even when OFF; promo object identities cannot be updated in place. After a confirmed save, cleanup deletes only eligible native promo paths through the Storage API and acknowledges the durable manifest. Errors leave the saved design intact and expose Retry cleanup. Lost save responses retain the uploaded path for retry instead of uploading another copy. Unreferenced unfinished uploads receive a one-hour recovery grace period before they become eligible for cleanup. Legacy external image URLs remain readable for compatibility; new uploads use native storage.

Public access is restricted to the saved image for the currently visible phase of an enabled, valid campaign/catalog. Other drafts and future-phase photos cannot be signed anonymously. Signed URLs are transport-only; valid existing URLs are reused within their safe lifetime to prevent repeated image reloads, including temporary signing failures. Old and hidden custom-image failures fall back to the preset. Online/visibility recovery can retry the working path.

The existing v2 backup already includes this bucket and store_settings, so custom photo binaries and metadata are backed up/restored without a new table manifest or format. Existing reset defaults clear `offer_*` configuration and put promo files into its existing file cleanup manifest. A full local backup → reset → file cleanup → restore roundtrip passes, including post-restore saved-photo protection. StorageMeter already sums all files in the hero bucket; its label now explicitly includes promo photos. The owner promotion panel shows measured byte usage including staged/pending files and refreshes after save/cleanup failures. No provider quota is invented.

Built-in assets remain website files. The original SVG print is24,272bytes; the offline Remotion decoration is101,554bytes,4sec/60FPS/720×360,H.264/YUV420p, silent. No Remotion player/runtime is an app dependency. The clip loads only in view, plays once and pauses offscreen/hidden; motion OFF/reduced-motion/Data Saver/slow2G retain static artwork. Only countdown digits tick; the grid/photos do not. Optional configuration loading never blocks initial products.

Coupon value, threshold and cap come from the selected real public coupon; checkout remains authoritative. Display dates do not create discounts or modify coupon validity. Save requires scheduled live times to fit the coupon window. Inactive/private/expired/exhausted coupons are suppressed. Future coupons are previewed only in a scheduled advance phase; no Copy/redeem action is shown there. Each successful public response anchors its configuration and server time together, using monotonic elapsed time for phase/countdown updates. Calendar actions download an importable ICS file; they do not promise device notifications. Copy success requires clipboard confirmation, with the existing manual-copy fallback.

## Validation

Local checks use intercepted synthetic catalog/owner services or an offline PostgreSQL container; no live transaction, message or database write is used:

- Unit tests: exact phase boundaries, schema limits, external links, countdown and UTF-8/escaped calendar export.
- PostgreSQL: repeatable install, owner-only RPCs, stale saves, rollback, future/limited coupons, unchanged existing financial definition.
- Public browser: held optional read does not block the collection, separate audiences, 1/2-product layouts,320/390/768/1440 widths, calendar download, device clock skew, advance/live/expiry, full custom artwork and no reduced-motion video request.
- Owner browser: independent audiences/presets, actual browser compression and mocked private Storage API uploads, path-only metadata, failed-save path reuse, cleanup ordering/failure/retry, and removing a photo back to its preset. No external hosting requests.
- Full-schema offline PostgreSQL audit: owner/staff/anon access, phase-specific public images, immutable/saved-photo protection, actual size/path checks, durable cleanup/orphan grace, backup/reset/restore, usage totals, and byte-for-byte unchanged financial/maintenance function definitions.
- Legacy offer browser: inline placement, actual minimum/caps, copy/manual fallback, offer OFF, all three languages, dark mode, motion controls and no timed popup.
- TypeScript, scoped ESLint, production build and whitespace checks.

The checked screenshots use example offers and local test product photos; no demo campaign is seeded in production. Re-render instructions are in `tools/catalog-promotion-remotion/README.md`.
