# Reset with business allocation reclaim (0029)

The owner requires confirmed resets to release the old business tables' allocated space, rather than only deleting their rows. A nonzero baseline still remains for tables, settings, users and maintenance metadata; there is no promised zero-byte database.

Apply `0029_reset_reclaim_allocation.sql` once through authorized SQL access, without replaying earlier migrations. A transactional ready-to-run copy is at `/workspace/review/apply-0029-reset-reclaim-only.sql`. **Applying it replaces a function definition; it never invokes reset, restore or business-data deletion.** `reset_reclaims_allocation = true` verifies installation only, not that a reset was performed. Publish the frontend for the new result display.

Only the existing `reset_store_data_v2` definition changes. Its signature, owner/RESET/verified-backup checks, shared lock and post-wait owner recheck stay intact. It atomically truncates a fixed list of all 20 business tables plus the product-linked hero singleton, with `CONTINUE IDENTITY RESTRICT` and no CASCADE. This releases their old heap/index files; unknown foreign-key dependencies block the operation and roll it back rather than clearing unrelated tables. Existing writes/readers may make its stronger table lock wait; the existing five-second lock timeout still applies. Pause other billing/editing sessions as the reset UI instructs.

The hero is captured before truncation. If design preservation is selected, its saved image and appearance are restored, its deleted product link is cleared, and its version timestamp advances so stale editor drafts cannot save over it. Other preservation options, owner login, Auth accounts, staff-access revocation, durable photo cleanup and optional bill counter restart at 1 retain their existing policy. No storage metadata is directly deleted by SQL. Uploaded files still clean up through the existing Storage API only after commit.

The reset result adds physical public-table allocation bytes before/after and their nonnegative difference. New clients display these as **Last reset: database allocation** and **Reclaimed allocation**, even when subsequent photo cleanup needs retry. Older servers/clients remain compatible: the frontend only shows this summary when valid server measurements exist. Photos and base/maintenance records are separately accounted for. Restoring a backup legitimately allocates space again.

Validation: disposable network-isolated PostgreSQL 17 with actual `pg-safeupdate`; applying the definition twice preserves complete business/settings snapshots and function grants/owner; fixed reset reclaims over 3 MB of seeded business-table allocation; restore round-trips every business table including costs; injected failures and unknown FK dependencies roll back; preserved hero/theme/operational preferences, hero version protection, last owner, roles and restart-at-1 checks pass. Browser fixtures validate the returned before/after summary and that cleanup failure does not cause a repeated reset. TypeScript/lint and production build also pass. No live reset or live compaction was executed by Codex.

For resale, use a genuinely separate fresh backend and verify its project ID/data before handover. Original database allocation is not transferred into a fresh database, but copying a frontend while retaining its original backend connection is not isolation. A fresh installation still has its own base footprint.
